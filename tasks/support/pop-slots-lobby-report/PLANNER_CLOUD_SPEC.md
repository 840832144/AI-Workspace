## 3. 策划阅读版的写法

正文只围绕“画面中发生什么、对玩家体验有什么作用、有什么值得借鉴、哪些仍要讨论”展开。采用完整中文短段落，必要时用简短表格；不是开发需求、复现教程或证据审计记录，也不能只给几条过于空泛的结论。

- 不搬入代码、函数名、类名、接口、引擎、状态机、座位快照、采样方法、技术证据分级等工程说明；不在云版末尾再附一大段同样难读的技术附录。技术研究原文保存在原材料中，不用模糊改名替代真实技术事实。
- 玩家能看到的用语可以保留，如机器人、机台、空位、入座、中奖、头像；BIG WIN/HUGE WIN 若对应画面，首次配中文说明。不使用英文工作流词或压缩缩写充当正文。
- 将研究问题译成体验问题。例如“跨界面座位一致性”写成“进入机台后，旁边还是不是刚才那批人”。这只是改变问法，不能把尚未确认的 Pop 规则写成已实现。
- 正文不展示 Task/commit/哈希/分支/本机路径/Review 流程，也不让策划先理解 E01–E19、W1/W2、D01–D12。必要来源改成图注时间、原需求标题和章节；细项映射留在 Git 维护记录。
- 保留观察与建议的区别，但不在每段堆叠专业标签和免责声明。自然使用“本次画面能看到”“此前研究认为”“还没有确认”“可以讨论”。在相关结论旁保留必要限制，末尾集中列其余问题。
- 不新增复杂公式。涉及原案人数关系时用已有条件算术举例，标明是假设比较，不是实测人数或 Pop 配置，不改变 CR 原值。完整推导留在私有原稿。

机器人结论可采用以下等价表达：“此前研究认为，Pop 很可能用机器人补充大厅人数。但具体哪些角色是机器人，以及如何补位、让座，目前还没有确认。”不能写成已逐个识别，也不能因为本片没有证明就删除此前研究的判断。

## 4. 文档一：Pop! Slots 大厅氛围拆解｜策划阅读版

开头用短段说明这份报告看什么，并给出几条最重要的体验结论；研究范围只需说明主要依据已有研究和约一分钟录屏。

建议顺序：

1. 大厅为什么显得热闹：围绕机台的角色、通道活动和中奖提示怎样共同呈现。
2. 人是怎样分布的：配坐席图，讲清所选局部镜头的人数和空位；不把少数截图说成全场固定规则。
3. 人物怎样活动：配连续截图，只讲画面已出现的站立、转向、行走和在座动作，不补写机器人完整自动循环。
4. 玩家怎样找到能玩的机台：配空位引导与锁定图，区分“空着”和“自己能玩”；点击有人座位后的反应仍未确认。
5. 中奖怎样让大厅更有动静：配中奖提示与展示屏图，区分界面表现、宣传轮播与实际奖励；不将短片计数写成长期概率或间隔。
6. 哪些值得借鉴、哪些需要取舍：用已审稿中的体验分析作归纳，不引入新方案参数。身份连续性和进出机台后是否还是同一批人，按原稿简要说明已知与未知。
7. 还需要进一步确认的问题：让座、完整活动过程、进出前后人物一致性等用简短问题列出，不展开技术补证方案。

六张原配图全部保留其有效内容，可调整顺序，图号、图注和正文对应。每图告诉策划“重点看哪里、能说明什么”，只保留必要时间码，例如“录屏 01:07”；无须展示毫秒或采样间隔。图中包含工程式编号时在维护副本记录对应，不要求读者理解原编号。

末尾仅放简短资料来源及进一步查阅入口。正文应可独立读懂，不依赖策划打开 Git、证据 CSV 或技术附录。公开 Pop 源稿不得包含 CR 私有参数；两份公司云文档间的互链只保存在获准内部发布记录。
