## 3. 必须修复项

### R1 — 客户端允许旧状态覆盖新状态（P1，源码缺陷）

**依据：** `Unity/Assets/Scripts/BingoClient.cs:35–36,54–74`。轮询只在发起GET之前判断 `!sending`。已有GET等待期间，玩家可以发起POST；两条协程都在完成时直接给 `state` 赋值，没有比较revision、请求代次或会话身份。

**反例路径：** 服务先处理GET，得到Selection/revision 10；随后处理start，得到Playing/revision 12。POST回包先应用、早先GET回包稍后应用，画面就从Playing退回Selection。即使服务端正确拒绝随后过期动作，客户端仍可短暂退阶段、撤回填格显示或对错误快照接受下一次用户点击。回包乱序是代码允许的时序，不声称已在这次User试玩发生。

**做什么：** 使用一个统一状态应用入口，或将所有状态GET与动作POST放进同一串行请求通道；保证较早快照不能覆盖已应用的新快照。采用版本门控时关联当前服务会话，不仅比较可能在服务重启后归零的revision；同revision时也不要让显示时间倒退。保持动作超时不自动换ID重发，别为此新增完整联网框架。

**成功表现：** 在实际客户端状态应用/传输边界，通过可控制延迟的替身验证GET晚到、POST晚到、开局/结束/返回转换和重复响应；已填状态与阶段不会倒退，动作不重复发送。再在本机正式原生入口验证一轮。

**失败怎么办：** 定位该请求/状态边界，不修改游戏填格或Bingo规则来掩盖问题；合成回包测试与原生实测分列。

### R2 — 干净源码的构建入口缺少restore步骤（P2，移交缺陷）

**依据：** `tools/Build.ps1:7` 第一条构建为 `dotnet run ... --no-restore`，此前没有restore；提交归档不含 `obj/project.assets.json`。`README.md`与`docs/TRANSFER.md`把Build作为开发机正式构建入口，没有声明必须先运行Review的Recheck或另一条恢复命令。

Microsoft官方CLI说明：`--no-restore`关闭隐式依赖恢复，构建需要restore生成的资产文件。因此按当前说明从干净源码直接Build会在规则阶段缺少前置，开发机已有缓存不能证明交接可重建。本轮未在.NET环境执行该失败，结论来自完整脚本、归档内容与CLI契约。

**做什么：** 首次构建显式restore并检查退出码，或取消首个命令的 `--no-restore`。可以继续复用后续 `--no-build`；不要求把bin/obj、SDK或缓存提交到Git。

**成功表现：** 从新目录解压源码、没有项目bin/obj和既有artifacts，在已安装合法工具的开发机按文档仅运行正式构建入口，规则、Unity导入和构建通过，再产生独立新包。记录准确源码/配置/产物版本。

**失败怎么办：** 报具体依赖错误和标准修复，不通过复制开发机obj/cache把缺失的前置隐藏起来；不更改系统策略绕过拦截。

外部参考只用于此CLI行为：Microsoft Learn `dotnet run` / `dotnet build` / `dotnet restore`，访问2026-10-16。
