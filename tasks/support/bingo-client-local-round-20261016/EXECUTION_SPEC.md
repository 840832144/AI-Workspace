## 3. 一局的范围与验收定义

首个交付锁定一个参考版本、一个普通房间、单卡、一个普通Bet、本地测试票。固定合成牌面和叫号，用于重复调试；不使用真实账号卡面或逐笔余额。原客户端画面、按钮和已有动画是实际承载界面，不另造界面冒充它。

| 环节 | 必须达到的结果 | 允许的首版简化 |
| --- | --- | --- |
| 启动和大厅 | 经正式启动入口连接本地服务，进入原客户端大厅；能够检查和停止自有进程。 | 仅一个可用房间；不实现无关入口后台。 |
| 选卡/门票 | 原选卡界面能确认或取消；取消不扣本地测试票，确认进入单卡局。 | 一个普通Bet即可，不做39档、等级解锁或完整经济。 |
| 发卡/叫号 | 原卡面与本地合成牌面一致，FREE和号码索引正确；多个号码按本地时序持续出现。 | 可以使用配置化的短测试局；明确不是已还原原服随机算法。 |
| 手动游玩 | 玩家通过正常界面连续填格，服务处理对应动作并与客户端状态一致；重复/非法动作不制造额外填充或Bingo。 | 不做自动填数字、策略机器人或GM控制台。 |
| 道具 | 至少一种该参考模式确实支持、会改变局内状态的基础道具，走“填格充能→可用→正常使用→真实效果/反馈”闭环。优先单格或双格填充，按实际证据选择。 | 不要求这一版恢复全部九道具或所有稀有度；不能只显示图标、不执行效果。 |
| Bingo | 使用已核对的判型/声明路径至少形成一次合法Bingo，客户端有对应结果/表现，本地状态不重复累计。 | 不以强发成功通知、改内存填满或任意Pattern编号代替合法过程。 |
| 结束与退出 | 按该测试场景的正常结束路径进入结果、完成必要的本地结算应答、返回大厅。 | 不发线上奖励，局外系统使用经验证的最小本地应答。 |
| 可重复开始 | 返回后可以重新选卡并初始化新局，没有旧局号/球/卡/buff残留。 | 无需第二局完整跑完；不新增十局、高填充率或多卡验收门槛。 |

需要保持交互性：改变一个普通点击会导致相应不同状态，不能只播放固定录像或与输入无关的预录响应序列。固定牌库/出球可以保留；玩法结果不能全部写死。

以上是本次最小闭环的采用范围，不宣称已经恢复完整原版。多卡、完整道具池、Bet/房间上限全表和便于团队分发的表现增强，作为之后一个扩展目标记录，不自动执行、不挤占这一局的交付。

## 5. 内部推进方式：连续做到可玩，不设置微型审批门

内部可以按以下三条工作线并行；它们不是三个需要提交Review后才继续的任务。

### 工作线A：足够支撑一局的协议和规则恢复

做什么：复用已有REA CLI/IDA/元数据及日志；先修v2实际使用路径的M1–M3，再按启动→单卡→叫号/动作/道具→Bingo/结算/离房追踪必要Schema、类型注册、序号域和真实传输封包。消息编号以更正索引和消费者方法交叉验证，不复制v1硬编码列表。

成功表现：兼容服可以处理本局所需的消息和事件；字段号、准确类型、集合/嵌套、可选默认值、压缩/长度等依据明确；合成消息体用独立解析路径检查。Type枚举、protobuf字段号和内存偏移分开。

失败怎么办：继续定位实际读写/注册/消费者方法或已有受控证据；只恢复缺的必需部分。字段未知是执行者的研究待办，不是自动要求User判断技术事实。文档矛盾直接修正，不能靠给Unknown贴known、把空请求当接受或编造字段通过。

### 工作线B：最小兼容服务与独立环境准备

做什么：Codex从第一轮就搭本地服务骨架和合成会话，边拿Schema边补初始化、发卡、叫号、动作和结束处理；dsh同时查地址选择、回退、资源依赖和获准接入路线。已有规则内核可作复用或对照，不预设它能替代原客户端全部本地计算。

成功表现：最小服务可启动检查，必要应答有效，独立测试实例具备明确的接入/隔离/回滚方式。外围请求逐项采用“已证可空、需最小对象、尚待验证”的处理，不再一律空RESP。

失败怎么办：新增必要初始化字段或缺失资源由执行者补齐；普通服务/编译/解析错误修复后继续。确实涉及新增系统权限的按§6一次集中提出；等权限期间继续本地实现和静态研究，不做无关大平台。

### 工作线C：原客户端实际联调与交付

做什么：一旦已有可用且获准的接入路径，即进行原客户端局部联调；不等全部材料写完。将发卡、叫号、持续填格、基础道具、合法Bingo、结束返回串成一局；普通缺陷由两边自行修复、回归和重跑。

成功表现：一个冻结候选按§3完成连续可玩流程，留下实际客户端行为与服务状态的一致证据，交付后User按简短说明可再次试玩。

失败怎么办：保留版本和失败记录，定位实际断点后选择已有授权范围内的替代实现继续。一次解析失败、一个方法名找不到或一次局部测试失败都不是整任务停工条件。若必须新增外部权限/资源，报告确切缺项、已尝试路径和最小申请，不重复提交泛化可行性报告。

中途只记录实质进展和需要协作者处理的接口变更；不按测试数量、解析字段数量或文档版本号汇报“完成”。默认在可玩目标达成后统一Review；没有达成时如实报告当前最远可运行位置，不把“已写完代码”“自写codec自检”作为替代交付。
