## 4. 剩余工作一：建立跨来源时间关联，不靠移动窗口让样本过线

### 当前依据

`bv_autoplay.execute_target()` 用主机 `time.time_ns()` 记录发送；`bv_verify.replay()` 直接将其与客户端日志 `at_ns` 比较，并将购买抓包时间与日志扣减比较。时区解析已经修正，但所读路径没有独立的主机—设备—日志时钟关联证据。

上传入口记录第三局同目标客户端时间早于主机发送约 4.346 秒，购买扣减也早于现有购买前窗；当时没有独立校准证据。这只能支持“当前归属不足”，不能直接证明根因是固定时钟偏差、日志缓存、字段解释错误或某一次人工点击。本评审不作该根因定案，也不将 `actual_spend_mismatch` 解释为已经证实额外扣费。

### 做什么

复用现有只读设备访问和来源核验器，增加一次有界、无购买、无游戏点击的时间链路检查。先从现有来源查明每种时间代表发生、写日志、主机接收还是动作发送，区分主机墙钟、主机单调计时、设备时间和日志事件时间；不要因为都写成 UTC 就当成同一已校准时钟。

在既有授权允许的只读命令范围内，记录设备读数及主机读取前/后的时间区间，保留往返耗时、精度、设备/采集 epoch 和有效时段。对日志另行检查时间含义、源文件身份、增量偏移、轮转、缓存/落盘延迟；设备当前时间与日志事件时间的关系也须有依据。现阶段不修改设备或主机系统时间，不安装同步服务，不重启采集器、不扩权。

把有证据的时间关系封装为控制与独立核验共同使用的转换/校验入口，并保存原始时间及转换依据。支持非零偏移和不确定区间，不强求所有墙钟显示完全一致。能够在同一可信时钟或同一已验证事件序列内判断的关系优先在那里完成；跨来源关系只有在不确定范围足够支持具体先后/窗口判断时才作确认。无法判定的保留 Unknown，不能拿日志被读取的时刻冒充事件发生时刻。

将这项检查接入未来购买前的准备流程，而不是付出票券后才发现所有确认时间不可比较。既有代码和回放可先连续修复；不需要买第四局来调试日期格式或采样流程。

### 成功表现

离线/实际函数回归至少覆盖：已知正负时钟偏差、较慢日志读取、墙钟跳变/设备重启、未知时区、旧记录覆盖新快照、同格事件早于发送且无独立依据。能解释某次匹配为何可信或未知；不能用固定减去本局观测差值、放大两秒/十秒窗口或移除检查来制造成功。

形成一份不含账号与余额明细的时间链路摘要，并让新采集记录携带必要来源信息。只读设备检查沿用现有时长边界并记入共同账本；完全离线回放与设备控制运行分开记录。

### 失败怎么办

继续在本 Task 内修复具体采样/解析/绑定问题并完成不依赖该项的离线工作。只限制不可信关系所涉及的购买和成功认定，不把整个工具链退回重新开发。当前测得的偏差只能描述当前有效区间；不能据此回改第三局，更不能消除已确认的人工干预。

## 5. 剩余工作二：运行模式必须与程序行为一起展示

### 做什么

直接扩展现有入口，不另做界面产品。启动前和运行过程中在策划可见的控制台/现有状态入口显示明确模式，并与实际参数绑定：

- **单击定位：只自动点击一个目标，之后等待终态；其他格子闪动不表示程序漏点，本局不计算自动玩填充率。**
- **完整自动玩/正式验收：持续处理本局全部合法目标，显示当前局次、运行状态和停止入口。**

本轮只实现和离线验证这些显示，不启动新对局。模式、实际目标点击上限、是否计算正式指标、User 是否应操作，都进入会话元数据和交接摘要。不要只在说明文件写“定位”，而运行入口仍笼统显示“自动玩”。导航点击和目标格点击分别标明；不加新的逐步骤人工批准弹窗。

出现无法归属的客户端操作时先准确记录“未匹配”，不能仅凭这个字段指责 User。第三局另有 User 明确说明手动补点，属于有独立确认的人工干预，保留这层区别。明确人工接管的局不得用于无人自动玩的验收，但原始证据仍可用于来源排查。

### 成功表现

用实际 CLI 到模拟输入的回归证明：单击模式最多一个目标，提示与实际行为一致；完整模式处理多个不同合法目标而不是误带一次点击上限；停止、特殊效果、确认缺失和末局冻结仍符合原要求。合成整局测试报告为合成，不写成真机通过。该项不要求消耗新的票券。

### 失败怎么办

修正现有模式参数/状态显示和测试后继续，不改变历史会话标签，不把定位局事后改成性能验收局。
