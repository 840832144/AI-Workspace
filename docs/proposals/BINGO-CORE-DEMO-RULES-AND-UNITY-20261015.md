## 3. 核心玩法范围

### 3.1 大厅和门票面板

一个普通房间，完整实现大厅→打开面板→选择/取消→开局→手动游玩→结束→返回大厅→再次入局。

默认一张卡；暂定支持1/2/4/6张，最多六张。dsh确认原模式合法档位后优先采用其规则；若不能确认就保留1/2/4/6。Demo不实现成长解锁，使用配置maxUnlockedCards控制可选上限，试玩配置可开放六张，默认选中一张。

Bet按User要求只影响本地体力/门票消费，不改变牌面、出球、道具概率、充能、Bingo判定、结束节奏或奖励倍数。原版Bet是否确实只有这一作用另作研究。验收应固定场景比较不同Bet，除消费/显示外的局内事件一致。具体价格表可配置，未知时不得声称沿用原版计价公式。

### 3.2 牌库与出球

原版是牌库还是随机生成尚未下结论。按User回退方案，首版采用固定场景库：scenarioId对应固定卡面集合、固定出球顺序/时序、Bingo计数脚本；可选择不同场景获得不同对局。不是仅固定seed却让不同点击导致出球变化。

卡面、出球、道具抽取/选目标分别记录。每个场景提供足够六张的合法卡面和明确选择规则；1/2/4/6选择只取合法子集，不复制同卡凑数。可分发场景使用自制合成卡面，不直接打包真实账号会话或Raw。

### 3.3 Bingo剩余计数

User判断为开局生成一个数字，其他人的Bingo会使其减少，到0结束；“其他人可能是假的”仍是User假设，不能写成已证实机制。

Demo用独立字段remainingBingos表示剩余计数，不混同秒数。初始值范围/候选表和otherBingoSchedule均配置化；固定场景固定其实际值与扣减时序，普通场景选择可随机。无需展示其他玩家或建设多人后端。自身Bingo/魔方Bingo是否扣减、一次扣多少、是否影响末段时间，列入dsh核验；未验证时采用明确标注的Demo配置，不由UI动画驱动扣数。

### 3.4 结束与收尾

推荐规则阶段：Playing → Closing（停止正常叫号/人工填格）→ EndBonus（执行已获得的结束补填与合法连锁）→ Result → Lobby。

这是一种实现结构，不是原版阶段名。User明确要求结束后补填，所以计数到0不能立即把所有规则逻辑销毁。EndBonus不重新开启普通玩家输入，不重复进入结算；结果只生成一次。原自动玩的300秒看门狗不是Demo玩法结束规则，不能导致已结束的试玩必须由人清理残留弹窗。

## 4. 九种道具：按User描述逐项保留

以下中文短名和ID是Demo命名，不冒称原版名称。每次作用对当前所选全部卡面分别处理，无目标的卡跳过且不影响其他卡。

|分组|Demo ID / 短名|User暂定规则|首版效果范围|
|---|---|---|---|
|Normal|N1 / 单格填充|每张卡随机填充一个空格。|真实改变格子状态，按规则处理Bingo与连锁。|
|Normal|N2 / 金币标记|每张卡随机一个空格增加金币加成buff。|落标记、保留触发和消耗表现；不发金币、不建立金币系统。|
|Normal|N3 / XP标记|每张卡随机一个空格增加XP加成，并让其它XP空格buff消失。|保留放置及清除；不发XP、不做升级。清除发生在放置规则中，不擅自改为填中后清除。|
|Rare|R1 / 双格填充|每张卡随机填充两个空格。|真实改变格子；同一卡两个目标不重复。|
|Rare|R2 / 宝箱标记|每张卡随机一个空格增加宝箱buff。|落标记并显示触发；不建宝箱/开箱/背包系统。|
|Rare|R3 / 炸弹|每张卡随机一个空格增加炸弹；炸弹格被填后向相邻四个方向填充。|真实触发邻格填充；距离、链式引爆、其它buff触发按核验/暂定策略处理。|
|Epic|E1 / 结束补填|对局结束后增加一次对所有卡面的随机空格各填一格。|登记本局收尾效果，在EndBonus执行；不是立即填格，也不是多叫一个球。|
|Epic|E2 / 魔方|每张卡随机一个空格增加魔方buff；该格被填后直接计算达成一次Bingo。|生成一次有来源的Bingo事件；不要求先形成直线，不把整卡全部填满。|
|Epic|E3 / ×2标记|每张卡随机一个空格增加×2buff；该格被填后结算奖励×2，且其它×2空格buff消失。|保留填中触发、倍率标志和清除表现；没有奖励账本，不实际发奖励。清除时机与XP不同。|

金币、XP、宝箱、×2的“奖励不实现”不等于删除道具、标记、触发或随机池位置。卡包等其它局外表现若需要可作为显示占位，不自动新增第十种道具。原图不能作为概率配置；三档/九种的取得、抽取、库存、充能、冷却和手/自动使用方式需dsh核验，未定数值用清楚标记的试玩配置。

### 4.1 需要二次核验但不阻止开发的边界

- “空格”是否包含已挂其它buff的未填格，是否排除FREE、已声明Bingo卡；卡上目标不足时的行为。
- XP和×2的“其它”作用于同卡还是全局；×2多次触发是保持2还是叠乘；已触发标记不应因“清空空格buff”被误清。
- 炸弹是上下左右紧邻一格还是沿方向扩展；炸弹击中炸弹/魔方/奖励标记是否连锁；连锁是否再充能。
- 结束补填多次使用如何累积；先结束补填还是先封存Bingo；补填触发魔方/炸弹及再次Bingo的规则。
- 魔方Bingo与普通线型Bingo是否可同时计数，同卡可获得几次Bingo，声明后的卡能否继续填格。
- 充能、道具获取/触发、效果数量与卡数关系、真实结束脚本及自身Bingo计数。

工程可先采用DemoAssumption配置来跑通：FREE不作随机目标；随机目标无放回；目标不足时作用全部可用目标；炸弹默认仅上下左右紧邻一格且不跨边；XP/×2清除暂按同卡未填同类标记；同一buff实例只触发一次；结束补填每获得一次累计一轮。上述是待确认的实现约定，不是User已明确的所有细节，更不是原版结论。

避免特定临时约定散落在界面代码；当dsh提供不同证据时，只更新规则配置/对应处理器和对照案例。

## 5. 推荐架构与迁移承诺

鉴于技术团队用Unity，推荐从一开始把唯一规则实现放在C#：

Unity表现层 → 本地传输适配 → .NET本地规则服务 → Bingo.Core（纯C#）
                                          ↘ 场景/配置/事件记录

Bingo.Core不依赖UnityEngine、MonoBehaviour、协程、画面坐标或数据库；规则时间、随机来源和输入显式注入。它负责合法性、填格、buff、事件队列、Bingo、结束补填及本局状态。本地服务是状态权威，客户端仅发动作和表现事件，不在两边各写一套裁决。

先核对团队Unity版本和可复用模板、现有Editor/构建模块及运行环境。核心库目标以团队支持的.NET Standard版本为准；现代.NET服务宿主与供Unity使用的兼容核心库分开构建，不能把整个服务端宿主DLL直接拖入Unity。

Windows可执行试玩包为首选交付：启动器拉起本地服务及游戏，失败显示明确原因，退出清理本Demo进程；试玩者不用安装Unity Editor、IDA或模拟器。客户端打包与服务自包含发布复用官方能力。Web试玩为后续可选构建，不让浏览器平台适配拖住第一版。

若本机Unity构建条件短检查无法建立，可先用Phaser/Vite等成熟模板做浏览器表现层，仍连接同一C#规则服务。不要先做TypeScript规则再承诺未来一键翻译C#。切回Unity时可直接复用规则库和协议；浏览器界面/动画仍需实现Unity表现，不承诺自动转换UI。

### 5.1 真正可“一键移交”的范围

- 统一的版本化消息合同、DTO、枚举、错误码与配置结构；生成/导出Unity可用类型和测试样例。
- Bingo.Core打包为独立C#库/UPM包；同一份源码可在Unity与本地服务测试，不是复制维护两份。
- 场景包包含卡面、出球、计数脚本、道具脚本/随机记录；明确行列与格子索引规范，来源适配器负责旧列优先编码转换。
- export-unity/import-package类脚本只搬运、生成和编译已明确的合同/配置/核心包，并执行固定场景一致性检查，不翻译任意业务代码或自动恢复原客户端。

这些入口名称是交付建议，不表示当前已经存在。少量JSON配置足够，首版不做账号/匹配/活动/数据库集群/云部署，也不开发通用移植框架。

## 6. 难度评估

这是工程相对难度估计，不是实测工期承诺。当前未核实团队模板、本机Unity构建和dsh完整规则目录，因此暂不报确定日期。

|路线|首版难度|长期移交成本|建议|
|---|---|---|---|
|Unity客户端 + C#内核 + 本地.NET服务|中等；主要新增在UI、动效、可执行包和平台联调。|最低；规则和表现工程可交Unity团队。|首选，前提是现有构建环境可用。|
|浏览器表现 + 同一C#内核/服务|低至中；模板成熟，但要维护两种语言的接口类型。|内核/协议可直接复用，Unity表现仍需重做。|Unity构建暂不可用时的交付备选。|
|原客户端连接本地兼容服务|高且不确定；局内协议可读不代表启动/资源/账号/版本依赖已闭合。|取决于可用测试工程和兼容边界。|记录里程碑候选，先做有限可行性审计，不成为Demo前置。|

玩法本身最大的难点是效果组合、结束顺序和可复查保真，不是大厅三个按钮。重点用统一effect queue处理填格→标记触发→新填格→Bingo；去重按效果实例与事件处理，避免同一炸弹或魔方反复触发。动画结束回调不决定业务状态，双方事件顺序不依赖帧率。

## 8. 分步交付与验收

### 步骤一：优先级落库与构建短检查
做什么：记录TASK-0039执行暂停，保全现场；完成新编号预检登记；优先检查团队Unity模板和打包，不把研究工具安装变成试玩者步骤。
成功表现：新Task与原Task分离，能启动最小客户端+本地服务，实际模板/版本/构建结果明确。
失败怎么办：不扩大原任务；仅Unity构建不可用时采用浏览器表现+C#内核备选，已知玩法开发继续。

### 步骤二：一张卡完整闭环
做什么：用固定卡面/出球/计数脚本完成大厅、选票、开局、手动填格、Bingo、结束和回大厅。
成功表现：无需连原服，能够完整玩完并再次开始；取消面板不消耗测试票，旧局事件不污染新局。
失败怎么办：固定场景定位状态与输入，不用随机多开局碰运气。

### 步骤三：1/2/4/6卡与九道具
做什么：按本文规则覆盖多卡和全部九种道具。结果奖励不发放，但标记/清除/触发仍真实执行。覆盖炸弹连锁、魔方Bingo、XP/×2不同清除时机、结束补填。
成功表现：每个道具正常/边界/组合场景可重放；Bet变更只影响测试资源；不同帧率不改变规则结果。
失败怎么办：未知处保留UserProvisional/DemoAssumption并配置化，不删除道具，不把视觉效果当规则完成。

### 步骤四：一键试玩与Unity移交验证
做什么：打包启动/检查/停止入口，输出核心包、协议/配置、固定案例和差异清单。至少在目标Unity工程实际导入、编译并跑一个同输入同输出的案例，不能只导出一个zip称为可迁移。
成功表现：干净试玩环境无需开发工具即可游玩；1/2/4/6均可回大厅再开局；本地服务不访问原游戏系统；原版已证实规则与暂定规则可区分。
失败怎么办：修复启动器、兼容或交互问题；单元测试数不替代试玩闭环。原自动玩“十局填充率>90%”不作为此Demo完成条件，玩家可故意不填。
