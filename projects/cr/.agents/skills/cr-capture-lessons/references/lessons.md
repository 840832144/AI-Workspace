## CR-2026-08-14-001 Windows PowerShell 5 导致 SVN 中文日志乱码

- 日期：2026-08-14
- 状态：已解决（新提交链路；历史乱码不可修订）
- 场景：用可见 PowerShell 认证窗口，以 `wangkun` 提交 dev 卡包 Season 2 配表。
- 现象与影响：远端 `r6097` 作者正确，但 `svn:log` 已是乱码；2026-08-26 用户再次指出 `r6419` 的提交信息乱码，已提交 revision 按用户要求不修订。
- 已确认根因：Windows PowerShell 5 把 UTF-8 无 BOM 脚本中的中文常量按系统代码页误读；之后即使写成 UTF-8 日志文件，写入的也已是损坏字符串。
- 尝试与结果：使用 UTF-8 文件和 `--encoding UTF-8` 提交曾失败，因为字符串在写文件前已损坏；使用 `svn propset --revprop` 修正 `r6097` 失败，服务器未启用 `pre-revprop-change` hook。2026-08-26 改由 Python 3 接收完整 Unicode 字符串、写 UTF-8 临时文件并调用 `svn commit --encoding UTF-8 --file`，`r6423` 的 XML 日志回读得到完整中文码点，证明新提交链路已解决。
- 可复用方案：中文日志不得通过 PowerShell 命令行参数传给 Python 或 SVN，因为参数在进入脚本前也可能损坏。应先生成并逐字回读 UTF-8 日志文件，再让 Python 3/SVN 通过 `--file` 与 `--encoding UTF-8` 读取；禁止在 PowerShell 5 的 UTF-8 无 BOM 脚本或命令参数中内嵌中文日志。提交完成后立即回读 `svn log --xml`，发现乱码只报告事实，不制造无业务变更 revision 掩盖。
- 验证方式：提交后用 Python 读取 `svn log --xml` 原始字节并按 UTF-8 解码，同时核对 revision、author 和完整 message。
- 后续动作：`r6097` 只能由 SVN 管理员启用 revision-property 修改 hook 后修正；禁止制造无业务变更的新 revision 掩盖旧日志。
- 证据：历史乱码 `r6097`、`r6419`；正确中文日志 `r6423`；SVN 错误 `E175008 Repository has not been enabled to accept revision propchanges`；用户提供的版本日志截图。

## CR-2026-08-14-006 SVN 自动属性把 UTF-8 Skill 误标为二进制

- 日期：2026-08-14
- 状态：已解决
- 场景：对新建的 `cr-capture-lessons/SKILL.md` 执行 `svn add`。
- 现象与影响：SVN 显示 `A (bin)`，文件被自动设置 `svn:mime-type=application/octet-stream`，会影响文本 diff 和合并。
- 已确认根因：工作副本的 SVN 自动属性规则误判 `SKILL.md`；文件本身为 UTF-8，且不含 NUL 字节。
- 尝试与结果：读取原始字节确认文件有效；删除错误的 `svn:mime-type` 属性后恢复文本处理。2026-08-26 新增 Boxing/Miner Markdown 时问题再次出现，并发现既有《老虎机与调控》同样带空 `svn:mime-type`；在目标目录内以 ASCII `.` 配合 `--depth files` 删除这三个纯文本文件的错误属性。
- 可复用方案：新增 Skill 后检查 `svn status` 是否出现 `(bin)`，并用 `svn proplist -v` 核对；纯文本文件被误标时执行 `svn propdel svn:mime-type <file>`。
- 验证方式：再次运行 `svn status`，确认不再显示 `(bin)`；`svn diff` 能展示文本内容。
- 后续动作：检查团队 SVN auto-props 配置是否存在过宽的 `SKILL.md` 或无扩展名二进制规则。
- 证据：`SKILL.md` 原始字节零 NUL；错误属性值 `application/octet-stream`；`r6423` 新增文件输出显示 `(bin)`，后续属性修复提交可由日志路径复核。
