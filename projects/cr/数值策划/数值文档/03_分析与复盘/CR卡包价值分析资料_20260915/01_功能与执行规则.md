# CR 卡包功能与执行规则

## 1. 玩家循环

获得卡包 → 开包获得卡片 → 收集章节 → 领取章节奖励 → 集齐并领取普通册奖励 → 升级高阶册、重新收集 → 领取高阶章节和整册奖励。重复卡可贡献兑换星星，也可能用于社交交易。Joker 用于选择兑换卡片。

`CardAlbumCfg` 决定活动周期。当前普通册152张，19章，每章8张；高阶册168张、21章，每章8张。高阶使用普通章节及新增章节的完整卡池。

**升级高阶**：`UpgradeToPrestigeSeason` 先计算重复卡可兑换星星，清空当前赛季的卡片及章节进度，再初始化高阶章节，重置整册领奖状态，保留结转的星星。普通册首张卡本身不按重复卡额外补偿。估算整个赛季成本时必须分两轮收集。

## 2. 卡包 ID、展示道具与卡片 ID

- `CardPack.id`：一条开包规则的ID。同一个包通常有多条规则。
- `CardPack.pack`：实际卡包ID，如100001。建模首先按 `season + pack` 选规则。
- `CardPack.itemId`：展示/背包道具映射。多个不同 `pack` 可以共享同一 `itemId`，不能合并为同一种概率分布。
- `maxStar`、`maxStarCount`、`cardNum` 是描述字段；实际发卡由有效的 `typeN/starN/groupN/numN` 和固定 `cardIdN` 决定。例如 `maxStar=6` 的包也可能实际抽4/5星金卡。
- `CardList.cardId`：具体卡ID；`CardList.ItemId` 是道具映射。按 `seasonId + cardChapter` 确认归属。

## 3. 一次开包怎样抽卡

1. 按当前 `season`、`pack` 筛出 `CardPack` 规则，按 `weight` 随机选一行。
2. 在开包开始时固定玩家本季唯一卡数与高阶状态。
3. 依次处理槽位1—5。有效槽位必须满足 `type>=0, star>0, group>0, num>0`。`type=0` 表示不限类型。
4. 每次尝试先筛 `CardGroup`：组号相同，`seasonDayMin <= day <= seasonDayMax`，`progMin <= uniqueCount <= progMax`。普通册仅使用 `isPrestige=0` 的组，高阶可使用两类组。
5. 按卡组权重选章节，然后在章节内按卡类型和星级筛选卡片。卡片权重使用玩家 `UID % 10` 对应的 `weight_10_0…9`。这里仅保留权重档规则，无真实UID数据。
6. 执行章节补缺筛选，再按卡权重抽一张。若该 `cardId` 已在本包出现，重新尝试。每张最多21次尝试；失败后该张跳过。因此这是**限制次数的重复拒绝重抽**，不等同于理想的无限次无放回抽样。
7. 随机槽位结束后追加最多3个固定 `cardId`。固定卡使用另一条加入路径，可以累计同ID数量。
8. 整包计算完成后再写入玩家卡片状态。本包计算中的玩家唯一卡数、章节持有数量不会随每张抽取更新；本包去重列表会更新。

### 权重实现细节

卡包、卡组、卡片共用 `GetRandomWeight`：整数抽取范围为0到权重和W，首项判断使用 `<=`。因此在非负权重下，迭代首项概率为 `(w_first+1)/(W+1)`，其余项为 `w_i/(W+1)`。第一项为0权重仍可能得到一个点。

这与普通 `w_i/W` 有偏差。精确模型应复现该逻辑，并确认配置加载后的迭代顺序。CSV保留Excel行顺序，但本次没有验证服务端加载后的顺序。理想权重模型可作为另一组敏感性结果，不能默默替代代码。

### 章节补缺

`RegulationPlayerCard` 要求 `cardTotalNum>0`、`needNum>0`，该章持有总数（包含重复）达到 `cardTotalNum`，剩余缺卡数不超过 `needNum`，且当前候选集中存在未拥有卡，才改抽候选中的新卡。当前第三季21章均未满足正参数启用条件。`cardControl` 的名字不代表此代码分支会启用。

## 4. 重复卡、星星与换包

当前 `goldStarRate=150`，`funStarRate=200`。重复卡只计算每张卡保留1张之外的数量。

| 类型 | n张重复卡的星星计算 |
|---|---|
| 普通卡 type=1 | `starLevel × n` |
| 金卡 type=2 | 整数运算 `starLevel × n × 150 / 100` |
| Fun/Ace type=3 | 整数运算 `starLevel × n × 200 / 100`；本季168张收藏卡无此类型 |

整数截断会使批量计算不一定等于单张结果乘数量，例如1张5星金卡得到7星，2张合计15星。扣卡还有优先级与超额星星结余，不能用一个固定小数星值替代所有流程。普通重复卡保存在持有数量里，在兑换/升级高阶等步骤处理，不应统一假设一拿到就全部自动销毁。

| 消耗星星 | 获得卡包 | 数量 | 共用冷却 |
|---:|---:|---:|---:|
| 50 | 100001 | 1 | 43200秒 |
| 100 | 100002 | 1 | 43200秒 |
| 200 | 100003 | 1 | 43200秒 |
| 500 | 100004 | 1 | 43200秒 |
| 1000 | 100005 | 1 | 43200秒 |

五档额外金币均为0。换包后调用 `OpenAllCardPack`，会处理该季待开卡包。星星的价值因此取决于换哪档包、冷却、季末剩余时间和所缺卡片，不能把以上五个兑换比例同时设为无条件等价。

## 5. Joker、交易与生命周期

- Joker：本季公共配置有 `1000001/type4`、`1000003/type6`、`1000004/type7`，有效期均86400秒。`jokerTrade` 分别为1、1、0（0表示不限目标类型）。最终换卡方法校验类型、消耗Joker并加目标卡。
- 表注释称type4为4星Joker、type6为5星Joker，但所读服务端换卡方法未见对应星级限制；列表方法直接按 `type == jokerTrade` 过滤，`jokerTrade=0` 的通配规则也未在该列表方法展开。完整客户端选择与服务端约束仍需确认。不能只凭显示名称写成确定的可兑换范围。
- 交易/赠送合计每日上限5次。每次求卡最多4名好友。求卡冷却及三类邮件有效期配置为57600秒。单卡 `isTrade=1` 才允许相应入口。
- 多余卡的社交用途与拆星用途互斥地消耗存量，估值要扣除被放弃的另一种用途。
- 赛季结束会清理旧季可兑换星星口径；Joker也有独立过期处理。交易邮件跨季、手动延后开包、Joker跨季可选范围需要额外确认端到端行为。

## 6. 卡包来源及关闭替代

- 普通Spin：`SlotsCasinoDropCards` 按 `betIndex`、VIP区间、等级选最后一个符合条件的配置。FreeSpin跳过，功能未解锁跳过。`dropPro` 以10000为分母，当前各行200，单次合格Spin命中概率2%；再按三个 `cardWeight` 的实际总和随机卡包。
- Bet、VIP、等级影响包型分布。不可把 `cardWeight/1000` 当成概率；不少行三项权重之和不为1000。
- 付费：`Cardget.Cost` 是金额×100，`ForbidKey` 参与排除/赠送判断；同时需要 `PayDiamond` 的商品配置。组合商品的整笔价格不能全分摊给卡包。
- 奖励通路支持活动、战令、礼包、邮件、广告宝箱、存钱罐、寻宝等。该列表来自代码入口，不证明所有入口当前都开放或有投放量。本包没有声称覆盖每个活动的完整投放计划。
- `CardActivityClose` 为指定活动的关闭替代；`ItemExchange` 是功能未解锁时通用转换链的依赖。替代奖励价值属于另一玩家状态，不能与已解锁卡册收益累加。
